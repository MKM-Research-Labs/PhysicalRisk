23.8 From PoC to Production: What Changes
================================================================

SECTION PURPOSE
---------------
Honestly assess what the PoC demonstrates vs what production requires. The PoC
proves the architecture works end-to-end; production adds scale, live data,
distributed compute, and enterprise integration.

WHAT THE POC PROVES
---------------------
The PoC is a complete, functioning trading desk that:
- Prices PRS using CDS mechanics with flood hazard rates
- Books trades as CDM-compliant PhysicalSwap records
- Computes daily MTM, Greeks, and P&L decomposition
- Manages close-out with T+2 settlement
- Generates EOD snapshots and PDF reports
- Stress tests against 260 historical storm scenarios
- Trains per-gauge GBM flood classifiers (AUC 0.92-0.95)
- Tracks 16 models with full governance (inventory, audit, MRC, BCBS 239)
- Maintains CDM records for properties, mortgages, gauges, counterparties
- Runs 6,047 automated tests with coverage reporting
- Generates 38 documentation packages (model docs, parameter inventories,
  governance artefacts)

This is not a mockup. It is a working implementation that proves the
integration architecture is sound end-to-end.

WHAT CHANGES FOR PRODUCTION
------------------------------

1. DATA: SYNTHETIC -> LIVE
   PoC: Uses synthetic property, mortgage, and gauge data generated via
   "python3 app.py port" command. Properties, mortgages, and storm events
   are algorithmically generated for the Thames catchment.

   Production: Requires live data feeds:
   - EA gauge telemetry (public API, 15-minute updates -- ready to integrate)
   - Real property data (Land Registry, EPC, OS MasterMap -- standard
     mortgage origination data already in bank systems)
   - Real mortgage portfolio data (already in bank systems)
   - Real counterparty data (already in bank systems)

   Gap assessment: The data transition is straightforward because the PoC's
   CDM schemas match real-world data structures. Property CDM uses UPRN,
   EA flood zones, ground level elevation -- all standard mortgage origination
   fields. The synthetic data was designed to be schema-compatible with
   production data.

2. SCALE: SINGLE CATCHMENT -> NATIONAL / MULTI-CATCHMENT
   PoC: Thames catchment only (40 gauges, ~200 properties).

   Production: Multiple catchments, potentially national coverage.
   - EA operates ~4,000+ gauges across England
   - Hazard curve fitting scales linearly with gauge count
   - GBM classifier training: ~1 hour per gauge (parallelisable)
   - Property-gauge linkage: one-time geographic computation per portfolio

   The PoC's multi-catchment architecture is already built into the CDM
   (CatchmentID field in all CDM records) and the routing layer
   (catchment selection at application startup). Extending to new catchments
   is a data exercise, not an architecture change.

3. PERFORMANCE: LOCAL -> DISTRIBUTED
   PoC: Runs on a single machine (Flask server on localhost).

   Production: Requires distributed compute for:
   - Portfolio-scale stress testing (1,000 Monte Carlo paths x thousands of
     properties x 260 scenarios)
   - Real-time gauge monitoring across thousands of gauges
   - Concurrent pricing requests from multiple traders/counterparties
   - EOD batch revaluation of large trading books

   The PoC's architecture (Flask API + JSON data store) would be replaced
   with enterprise infrastructure (load-balanced API, database, message
   queue, compute cluster). The business logic (pricing, risk, P&L) is
   unchanged -- only the deployment infrastructure scales.

4. INTEGRATION: SELF-CONTAINED -> FDC3/CDM ECOSYSTEM
   PoC: Self-contained application with its own UI, API, and data store.

   Production: Connects via FDC3 to the existing desktop ecosystem:
   - CDM objects flow as FDC3 context payloads between applications
   - Intents trigger cross-application workflows (gauge alert -> risk
     recalculation -> collateral update -> capital impact)
   - App Directory registers PRS components for discovery
   - Desktop Agent Bridging connects to legacy systems

   Chapter 21 established that the FDC3 infrastructure exists and is
   adopted at major banks (BMO: 73 apps, Aladdin: FDC3 2.0 conformant).
   The PoC's API endpoints map directly to FDC3 intents and context types.

5. PRICING: ANALYTICAL -> QUANTLIB
   PoC: Uses analytical CDS pricing (implemented from first principles).
   QuantLib integration functions are prepared but not live.

   Production: QuantLib CDS engine provides:
   - Standard ISDA pricing compliance
   - Multi-engine validation (ISDA, Integral, Midpoint)
   - Hazard rate curve construction via SurvivalProbabilityCurve
   - Industry-standard CS01/DV01 computation

   The analytical engine and QuantLib produce identical results (both
   implement the same quarterly CDS mechanics). The switch is a
   configuration change, not an algorithm change.

6. TRIGGER LOGIC: BASIC -> FULL
   PoC: Implements "Any" trigger type only (single gauge breach triggers).

   Production: Full GaugeSet evaluation:
   - "Any": single gauge breach (implemented)
   - "All": every gauge in basket must breach
   - "Weighted": weighted sum exceeds threshold
   - "Majority": more than half of basket must breach

   The CDM schema already defines these trigger types. Implementation
   requires extending the GaugeSet evaluation function -- bounded work.

7. REGULATORY REPORTING: GENERATED -> SUBMITTED
   PoC: Generates BCBS 239 self-assessment, model documentation, parameter
   inventories, MRC Terms of Reference, test results reports -- all as PDF.

   Production: These documents are submitted to regulators:
   - BCBS 239 evidence package to supervisory team
   - Model documentation to model validation team
   - MRC meeting records to audit
   - EOD reports to regulatory reporting systems
   - Capital impact calculations to ICAAP/ILAAP

   The content is generated by the PoC. The submission is an institutional
   process, not a technology gap.

THE VALUE OF THE POC
----------------------
The PoC's value is not as a production system. It is as proof that:

1. The architecture works: every component (pricing, booking, risk, P&L,
   stress, governance) has been built and tested end-to-end.

2. The CDS analogy is operational: not just theoretical but implemented in
   code that runs, prices, trades, and risk-manages.

3. The integration delta is bounded: the list of "what's new" is specific,
   finite, and each item has a working reference implementation.

4. The governance is pre-built: model documentation, parameter inventories,
   BCBS 239 evidence, audit trails, and MRC workflows are ready for
   regulatory review, not empty templates.

5. The risk is de-risked: a bank considering PRS integration can examine
   working code, run the platform, and assess the effort required --
   rather than evaluating a concept paper.

The PoC exists to prove that PRS integration into a bank's CDS risk
architecture is an incremental extension, not a transformational rebuild.
Everything in this chapter and Chapter 22 is demonstrated by running code.
