22.9 Integration Roadmap
================================================================

SECTION PURPOSE
---------------
Translate the preceding sections into a phased implementation plan with a clear
delta analysis: what can be reused vs what must be built, and in what order.

THE TRIGGER AND NOTIFICATION ARCHITECTURE
------------------------------------------
Once a PRS is booked, it follows the same infrastructure as CDS with one critical
addition: physical event notification.

  CDS infrastructure (reused as-is):
  Trade capture -> daily revaluation -> P&L -> margin/collateral -> EOD ->
  regulatory reporting -> close-out/settlement

  PRS addition (the notification layer):
  EA gauge API ---> Gauge Monitor Service
                         |
                    [gauge reading vs trigger level in GaugeSet]
                         |
                    If severe alert breached:
                         |
                    +----+----+
                    |         |
              Gauge-level   Property-level
              notification  notification
                    |         |
              PRS trigger    Mortgage book
              evaluation     impact cascade
                    |         |
              Settlement     LTV recalculation
              process        Capital adjustment

  At gauge level: GaugeSet evaluated (Any/All/Weighted/Majority logic),
  payout activated if trigger conditions met, settlement initiated.

  At property level: spatial model maps gauge breach to property-level flood
  depth, depth-damage function computes loss estimate, mortgage LTV recalculated,
  Frye-Jacobs conditional LGD applied, portfolio capital impact assessed.

PHASED IMPLEMENTATION
-----------------------

PHASE 1: MARKET DATA FOUNDATION (Weeks 1-4)
  Connect gauge data feed to existing market data infrastructure:
  - Integrate EA gauge API (public, free, REST, 15-minute updates)
  - Build gauge reference database (GaugeID, location, thresholds, history)
  - Register gauges as reference entities (analogous to Markit RED code onboarding)
  - Establish gauge monitoring service for trigger detection
  Dependencies: none (standalone data infrastructure)
  Reuses: existing market data distribution, reference data management

PHASE 2: PRODUCT REGISTRATION (Weeks 2-6)
  Register PRS as a new product type in CDM/trade capture:
  - Add PhysicalSwap to booking system product catalogue
  - Configure GaugeSet fields (basket structure already supported)
  - Set up pre-trade validation (validate_gauge, validate_swap)
  - Link PRS trades to existing counterparty and collateral systems
  - Configure T+2 settlement, ACT/360, semi-annual roll conventions
  Dependencies: Phase 1 (gauge reference data must exist for validation)
  Reuses: existing OTC booking, counterparty, collateral, settlement systems

PHASE 3: PRICING ENGINE EXTENSION (Weeks 4-8)
  Extend CDS pricing engine with flood hazard rate source:
  - Build GEV hazard curve constructor from gauge history
  - Implement basis waterfall (5 components)
  - Configure QuantLib CDS engine to accept flood hazard rates
  - Validate pricing against PoC analytical engine outputs
  - Implement Gumbel-adjusted multi-year survival curves
  Dependencies: Phase 1 (gauge data), Phase 2 (product registered)
  Reuses: QuantLib CDS engine, yield curve infrastructure, recovery rate framework

PHASE 4: RISK AND P&L (Weeks 6-10)
  Deploy flood models alongside existing model infrastructure:
  - Configure DeltaEngine for FS01 and basis DV01 computation
  - Add PRS to daily MTM batch (same revaluation engine, new risk factor)
  - Configure P&L decomposition (new trade vs market move vs running)
  - Add PRS to EOD snapshot and reporting
  - Implement close-out workflow with T+2 settlement
  Dependencies: Phase 3 (pricing engine must produce fair spreads and Greeks)
  Reuses: existing MTM, P&L, EOD, close-out infrastructure

PHASE 5: STRESS TESTING (Weeks 8-14)
  Extend stress testing framework with storm scenarios:
  - Import storm scenario catalogue (260 historical + synthetic)
  - Train GBM flood classifiers per gauge (40 gauges, ~1hr per gauge)
  - Connect storm scenarios to portfolio revaluation engine
  - Add spatial correlation to portfolio aggregation
  - Integrate Frye-Jacobs LGD adjustments for stressed capital calculations
  - Build property-level notification cascade for flood events
  Dependencies: Phase 4 (risk engine must be operational)
  Reuses: existing stress testing framework, scenario management, P&L attribution

PHASE 6: GOVERNANCE AND MRC APPROVAL (Weeks 10-16)
  Submit models through MRC approval cycle:
  - Register 16 models in bank's model inventory (tiered by materiality)
  - Submit model documentation packages (pre-built by PoC)
  - Present parameter inventories to validation team
  - Conduct independent validation against PoC test suites
  - Obtain MRC approval for production deployment
  - Submit BCBS 239 compliance evidence to regulatory reporting
  Dependencies: Phases 1-5 (all models must be operational for validation)
  Reuses: existing MRC process, model inventory system, validation framework

THE CONCLUSION
---------------
PRS does not require a new desk -- it is a new product on the existing CDS desk.
CDM means trades flow through existing booking, confirmation, and settlement.
Pricing uses the same QuantLib engine with a different hazard source.
Risk management uses the same MTM, Greeks, P&L, and EOD processes.
Stress testing extends existing frameworks with a new scenario type.
Governance artefacts are pre-built and follow bank-standard patterns.

When a gauge breaches its severe flood warning level:
- At the gauge level: the GaugeSet trigger logic evaluates, PRS settlement
  initiates, following the same notification and settlement path as a CDS
  credit event determination
- At the property level: the spatial model maps the breach to property-level
  flood depth, damage functions quantify loss, mortgage LTV is recalculated,
  and portfolio capital impact is assessed via Frye-Jacobs

The PoC exists to prove all of this works end-to-end. The integration is
incremental, not transformational.
