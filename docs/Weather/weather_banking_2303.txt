23.3 Trade Lifecycle via CDM
================================================================

SECTION PURPOSE
---------------
Walk through the complete PRS trade lifecycle as implemented in the PoC,
showing CDM as the golden source at every stage. Demonstrate that this
lifecycle is operationally identical to CDS.

LIFECYCLE STAGES
-----------------

STAGE 1: PRE-TRADE PRICING
  Input: gauge_id, trigger_level, tenor, notional
  Process:
    1. Retrieve gauge hazard curve (GEV-fitted exceedance probabilities)
    2. Convert exceedance probability to continuous hazard rate:
       lambda = -ln(1 - annual_exceedance_probability)
    3. Compute fair spread via CDS pricing engine:
       - Risky annuity = Sum(dt x S(t) x DF(t)) quarterly
       - Protection PV = (1-R) x Sum((S(t-1)-S(t)) x DF(t))
       - Fair spread = protection_pv / annuity x 10,000 bps
    4. Apply basis waterfall if portfolio-specific:
       + model uncertainty (+2bp)
       + distance to gauge (+0.5bp/km, capped +6bp)
       + elevation difference (-0.2bp/m, capped -3bp)
       + terrain / flood zone (-1 to +3bp)
       + composition (-1 to +2bp)
    5. Return indicative price with fair spread, NPV, premium/protection PVs
  Output: pricing summary for counterparty negotiation
  CDM: no record created yet (pre-trade only)

STAGE 2: TRADE EXECUTION AND COMMIT
  Input: agreed spread, counterparty, all pricing parameters
  Process:
    1. Select counterparty from CDM counterparty master
    2. Validate gauge: confirm GaugeID exists, flood stage thresholds valid,
       data quality checks pass (validate_gauge)
    3. Validate swap: required fields present, menu values valid, basket size
       plausible, GaugeIDs correspond to valid FloodGauge records (validate_swap)
    4. Create PhysicalSwap CDM record:
       - SwapID: "PRS-{uuid}" (unique, immutable)
       - Header: trade type, counterparty, T+2 protection start
       - LegData: Fixed, GBP, ACT/360, spread as fixed rate
       - ScheduleData: start, maturity (semi-annual roll), 6M tenor, London
       - GaugeSet: gauge basket with weights and trigger levels
       - Triggers: type (Any/All/Weighted/Majority), threshold
       - Payouts: currency, max payout
       - Pricing: trade spread, fair spread, NPV, leg PVs, annuity, curve, recovery
    5. Save CDM record as JSON: data/output/prs/PRS-{uuid}.json
    6. Generate trade confirmation PDF from CDM record
  Output: committed trade with CDM record, confirmation document
  CDM: PhysicalSwap record created as golden source

STAGE 3: DAILY VALUATION (Mark-to-Market)
  Input: all open trades, current market state (hazard rates, yield curve)
  Process:
    1. DeltaEngine loads each trade's CDM record
    2. For each trade:
       a. Retrieve current hazard rate for gauge/trigger from market state
       b. Compute current fair spread using updated hazard rate
       c. Compute risky annuity at current yield curve
       d. MTM = (fair_spread - trade_spread) / 10,000 x annuity x notional x direction
       e. Compute FS01: bump hazard rate +1bp, recompute spread, measure delta
       f. Compute basis DV01: sensitivity to basis spread change
    3. PnLEngine decomposes:
       - new_trade_pnl: full MTM if traded today
       - market_pnl: today MTM minus yesterday MTM
       - daily_pnl: sum of new + market
       - running_pnl: cumulative from inception
  Output: enriched blotter with MTM, Greeks, P&L per position
  CDM: PhysicalSwap Pricing section updated with current fair spread and NPV

STAGE 4: MARKET STATE MANAGEMENT (Intraday)
  The trader can adjust hazard rates and yield curves intraday:
  - POST /trading/market-state: adjust basis adjustments temporarily
  - POST /trading/yield-curve: adjust discount curve
  - POST /trading/hazard-term-structure: adjust gauge hazard rates
  - Commit: save adjustments as new base case
  - Reset: revert to original base case
  - All adjustments logged with timestamp for curve history audit trail

  This mirrors how a CDS trader adjusts credit spread assumptions intraday
  based on new information (earnings, rating changes, market moves).

STAGE 5: CLOSE-OUT
  Input: swap_id, agreed close-out spread
  Process:
    1. Retrieve original trade CDM record
    2. Compute settlement:
       settlement = (closeout_spread - trade_spread) / 10,000 x annuity x notional x direction
    3. Create new CDM record with CloseOutOf referencing original SwapID
    4. Update original trade: status -> "Closed"
    5. Save trade marks: close_date, close_spread_bps, final_pnl, settlement_amount
    6. Compute T+2 settlement date (skip weekends)
    7. Generate close-out confirmation PDF
  Output: closed position, settlement amount, confirmation document
  CDM: original record updated; close-out record created with linkage

STAGE 6: TRIGGER EVENT (Flood)
  Input: EA gauge reading exceeding severe flood warning threshold
  Process:
    1. Gauge monitor service detects breach
    2. For each open PRS referencing this gauge:
       a. Evaluate GaugeSet trigger logic (Any/All/Weighted/Majority)
       b. If trigger conditions met: activate payout
       c. Payout amount = PayoutSevereFlood from GaugeSet
       d. Initiate settlement process (T+2)
    3. Simultaneously at property level:
       a. Spatial model maps gauge breach to property flood depths
       b. Depth-damage functions compute loss estimates
       c. Mortgage LTV recalculated
       d. Frye-Jacobs conditional LGD applied
       e. Portfolio capital impact assessed
  Output: PRS payout settlement, property-level damage assessment
  CDM: FloodGauge CDM updated with event data; PhysicalSwap settlement recorded

STAGE 7: END-OF-DAY
  Input: EOD date
  Process:
    1. Revalue all open trades at EOD hazard rates
    2. Compute portfolio P&L summary (daily, running, by source)
    3. Snapshot market state, positions, P&L
    4. Save EOD JSON: EOD-YYYYMMDD.json
    5. Generate EOD report PDF (positions, P&L chart, market state)
  Output: EOD snapshot, report, audit record
  CDM: EOD snapshot references all active PhysicalSwap CDM records

THE CDM THREAD
---------------
The PhysicalSwap CDM record is the golden source from Stage 2 through Stage 7.
Every downstream system -- risk, P&L, collateral, regulatory reporting,
settlement -- reads from and writes to this record. This is identical to how
CDS trade capture systems maintain a golden record (DTCC Trade Information
Warehouse model) that downstream systems reference.

The CDM record flows through the same channels:
  Trade capture -> Risk engine -> P&L -> Collateral -> Settlement -> Reporting

Adding PRS to this flow is a product-type extension, not an infrastructure change.
