22.4 Market Data Infrastructure
================================================================

SECTION PURPOSE
---------------
Detail what data feeds PRS requires, what a bank already has, and what is new.
Show how gauge telemetry, storm catalogues, and hazard curves integrate as either
market data (for pricing) or scenario data (for stress testing).

WHAT THE BANK ALREADY HAS
---------------------------
- Yield curve feeds: government bond curves, swap curves, OIS curves
- Counterparty data: credit ratings, trading limits, business units, CSA terms
- Property and mortgage origination data: UPRN, valuation, LTV, loan terms,
  construction details, EA flood zone classification
- Market data distribution infrastructure: real-time feeds, intraday snapshots,
  end-of-day closes

WHAT PRS ADDS
--------------

1. GAUGE TELEMETRY (Real-Time Market Data)
   Source: Environment Agency real-time flood monitoring API
   Frequency: 15-minute updates
   Cost: Free, public, no licensing
   Content: water level readings at ~4,000+ gauges across England
   Integration: API-accessible, JSON format, standard REST endpoints

   This is the PRS equivalent of a credit spread feed. The gauge reading is the
   observable that determines whether a trigger has been breached. It is:
   - Objective: measured by government-calibrated instruments
   - Verifiable: published in real time by the Environment Agency
   - Historical: decades of archived data for model calibration
   - Free: no Markit-equivalent subscription required

   For PRS trigger monitoring, the bank needs a feed from EA gauge API that:
   - Monitors gauges referenced in open PRS positions
   - Compares current readings against trigger levels in GaugeSet
   - Raises alerts when readings approach or breach thresholds
   - Logs all readings for audit trail and settlement evidence

2. HAZARD CURVES (Pricing Data -- Analogous to Credit Spread Curves)
   Source: GEV fitting to historical EA gauge annual maxima
   Frequency: Recalibrated periodically (annually or after significant events)
   Content: exceedance probability at each threshold for each gauge
   Integration: computed internally from gauge history, stored as gauge metadata

   Hazard curves serve the same function as credit spread curves in CDS:
   - They are the input to the pricing engine's hazard rate
   - They define the term structure of flood risk
   - They are calibrated to observable data (gauge readings, not model projections)
   - They can be "bumped" for sensitivity analysis (FS01 = flood spread 01)

   In early markets, hazard curves are model-derived from historical data.
   As PRS markets develop and transaction volumes grow, market-implied hazard
   rates from traded PRS spreads will supplement or replace model-derived curves
   -- exactly as CDS markets evolved from model-based to market-based pricing.

3. STORM SCENARIO CATALOGUE (Scenario Data for Stress Testing)
   Source: Historical EA flood events, synthetic storm generation
   Content: 260 alert-breaching storms + 740 sub-alert storms for training
   Fields per storm: gauge responses (water levels over 168-hour horizon),
     peak levels, breach timing, duration, spatial extent
   Integration: stored as JSON, consumed by stress testing engine

   Storm scenarios are the PRS equivalent of credit stress scenarios. They
   serve the same function as credit spread shock scenarios in CDS stress
   testing -- they define "what if" conditions for portfolio revaluation.

4. PROPERTY-GAUGE LINKAGE DATA
   Source: geographic proximity computation (gauge locations vs property locations)
   Content: nearest gauges to each property, distance, elevation difference,
     EA flood zone, terrain classification
   Integration: computed at portfolio onboarding, stored in Property CDM

   This enables the basis waterfall calculation (section 22.2) and is
   analogous to linking a CDS reference entity to its sector, rating, and
   seniority -- enrichment data that feeds pricing adjustments.

DATA FLOW ARCHITECTURE
-----------------------
The PoC demonstrates two data flow patterns:

  MARKET DATA FLOW (for pricing and MTM):
  EA Gauge API -> gauge telemetry feed -> hazard curve builder -> hazard rates
  -> pricing engine (QuantLib CDS) -> fair spread -> MTM -> P&L

  SCENARIO DATA FLOW (for stress testing):
  Storm catalogue -> hydrograph synthesis -> GBM classifier per gauge
  -> P(flood) surface -> CDS-in-stress revaluation -> stress P&L

Both flows produce outputs in formats that existing CDS risk systems consume:
hazard rates, survival curves, spread sensitivities, scenario P&L.

DATA GOVERNANCE
----------------
All data sources in the PoC have full lineage documentation:
- Source identification (EA, NRFA, synthetic generator)
- Transformation steps (GEV fitting, basis calculation, classifier training)
- Version control (model parameters, curve dates, calibration epochs)
- Staleness monitoring (when was each data element last refreshed?)
- BCBS 239 compliance evidence generated by the platform

This data lineage infrastructure satisfies the governance requirements
established in Chapter 19 (Model Risk Governance) and Chapter 20 (CDM and
Data Framework).

INTEGRATION COST
-----------------
Standard/reusable: yield curves, counterparty data, property/mortgage data,
market data distribution infrastructure -- all exist
Novel/new-build:
- EA gauge API integration (public, free, standard REST -- low cost)
- Hazard curve builder (GEV fitting -- bounded, well-defined)
- Storm scenario catalogue (one-time build from historical data)
- Property-gauge linkage computation (geographic, one-time per portfolio)
- Gauge monitoring/alerting service (event-driven, straightforward)
